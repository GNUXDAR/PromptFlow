# PromptFlow コントリビューションガイド

> [スペイン語の原文](../../../CONTRIBUTING.md)からの翻訳です。内容に相違がある場合は原文が優先されます。

PromptFlow に関心を持っていただきありがとうございます！このガイドでは、誤字の修正から完全な機能の追加まで、変更を提案する方法を説明します。初回は最初から最後まで通して読み、その後は必要なセクションを参照する使い方を想定しています。

> **メモ：** オープンソースプロジェクトへのコントリビュートが初めてでも、すべてを完璧にこなそうと心配する必要はありません。善意の小さな PR は、PR がないよりずっと良いものです。残りはレビューでお手伝いします。

## 貢献の方法

貢献はコードだけではありません。次のどれもが貴重な貢献です：

| 種類 | 例 |
|---|---|
| **バグ報告** | 何かが動かない、表示がおかしい、あなたの環境でスクロールがなめらかでない。 |
| **アイデアの提案** | 新しい機能、ショートカット、原稿のフォーマット。 |
| **コード** | 修正、機能、パフォーマンス、テスト。 |
| **ドキュメント** | 誤字、説明の補足、例、図。 |
| **翻訳** | 新しい言語の追加や既存の言語の改善（[下記参照](#翻訳)）。 |
| **ハードウェアでのテスト** | Bluetooth ペダル、タブレット、Raspberry Pi、クライアント分離が有効な Wi‑Fi ネットワーク。 |
| **PR のレビュー** | 他の人の PR を試し、気づいたことをコメントする。 |

## 始める前に

### 既に存在しないか検索する

issue を作成したりコードを書き始めたりする前に、オープンな [issues](https://github.com/GNUXDAR/PromptFlow/issues) と [pull requests](https://github.com/GNUXDAR/PromptFlow/pulls) を検索してください。誰かが同じことに取り組んでいる場合は、作業の重複を避けるためにそちらにコメントしてください。

### 大きな変更は issue を作成する

| 変更の規模 | 事前に issue が必要？ |
|---|---|
| 誤字、リンク切れ、わかりにくい文章 | 不要：直接 PR を作成してください。 |
| 小さく明確なバグの修正 | 推奨、ただし必須ではありません。 |
| 新機能、動作の変更、プロトコルやアーキテクチャの変更 | **必要です。** 事前に方針を合意しておけば、設計上の意見の相違で作業が却下されるのを防げます。 |

> **ヒント：** issue に「私が担当します」とコメントして、他の人が同じものを手に取らないようにしましょう。後で続けられなくなったら、一言知らせてください。問題ありません。

### 最初に取り組む issue

`good first issue` ラベルの付いた issue は、範囲が限定されていて、初めての人向けに説明されています。`help wanted` の付いた issue は重要で、ボランティアを募集しています。

## 環境の準備

### 必要なもの

- [Flutter](https://docs.flutter.dev/get-started/install) stable（Dart 3）。
- Linux：Flutter のデスクトップ向け依存パッケージ（`clang`、`cmake`、`ninja-build`、`libgtk-3-dev`）。
- Android（オプション）：Android SDK と、実機またはエミュレーター。

### フォークとクローン

```bash
# 1. GitHub でフォークし（「Fork」ボタン）、クローンする
git clone https://github.com/<ユーザー名>/PromptFlow.git
cd PromptFlow

# 2. 元のリポジトリを「upstream」として追加する
git remote add upstream https://github.com/GNUXDAR/PromptFlow.git

# 3. 依存関係をインストールし、すべて動作することを確認する
flutter pub get
flutter analyze
flutter test
```

### 音声（オプション）

```bash
tool/setup_vosk_linux.sh      # libvosk + Linux 用スペイン語モデル
```

## ブランチモデル

| ブランチ | 用途 | 誰が書き込むか |
|---|---|---|
| `main` | リリース済みのバージョン。常に安定。 | メンテナーのみ、バージョンのリリース時に。 |
| `develop` | 次にリリースされる内容の統合。**すべての PR の宛先。** | 誰も直接は書き込まない：PR 経由のみ。 |
| `tipo/descripcion` | あなたの作業。テーマごとに 1 ブランチ。 | あなた。 |

> **重要：** `main` や `develop` に直接コミットしたり、`main` に向けて PR を作成したりしないでください。すべて `develop` への PR を通じて取り込まれます。

### ブランチ名

`tipo/descripcion-corta` を、小文字とハイフンで使います：

| プレフィックス | 用途 | 例 |
|---|---|---|
| `feat/` | 新機能 | `feat/follower-mode` |
| `fix/` | バグ修正 | `fix/pause-marker-skip` |
| `docs/` | ドキュメントのみ | `docs/protocol-examples` |
| `i18n/` | 翻訳 | `i18n/add-turkish` |
| `perf/` | パフォーマンス | `perf/painter-culling` |
| `refactor/` | 動作を変えない再構成 | `refactor/controller-commands` |
| `test/` | テストのみ | `test/remote-reconnect` |
| `chore/` | ビルド、依存関係、CI | `chore/bump-flutter` |

```bash
git fetch upstream
git switch -c fix/pause-marker-skip upstream/develop
```

## 変更を加える

### 1 つの PR に 1 つのテーマ

PR は **1 つのことだけ**を行うべきです。バグを修正している途中で別のバグを見つけたら、PR を 2 つ作成してください。小さな PR ほど早く、丁寧にレビューされます。

| 規模 | 推奨 |
|---|---|
| < 200 行 | 理想的。 |
| 200–600 行 | 許容範囲。説明で構成をしっかり説明してください。 |
| > 600 行 | 複数の PR に分割するか、issue を作成して分割を計画してください。 |

### アーキテクチャを守る

コードに触れる前に [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md) を読んでください。レビューで特によく確認されるルールは次のとおりです：

- `domain/` は Flutter のウィジェット、ソケット、ファイルに依存しない。
- すべての操作は `PrompterCommand` であり、キーボード、ペダル、リモコン、音声のどこから来たものでも `PrompterController.execute` を通る。
- アニメーションループ内でフレームごとにウィジェットを再構築しない。
- プロトコルを変更した場合は [`docs/PROTOCOL.md`](../en/PROTOCOL.md) を更新する。互換性を壊す変更の場合は `v` フィールドを上げる。
- ユーザーに表示されるテキストは `lib/l10n/` に置き、コードに直接書かない（[翻訳](#翻訳)を参照）。

### テスト

- バグ修正には、その修正がないと失敗するテストを付けること。
- ロジックを含む新機能（エンジン、パーサー、プロトコル、音声）にはテストを付けること。
- スクロールエンジンには `ScrollEngine.manual()` と `advance()` を使うこと：テストは決定的で、時計に依存しません。

### プッシュする前に

```bash
dart format lib test integration_test
flutter analyze        # 警告なし
flutter test           # すべて成功
```

## コミットメッセージ

[Conventional Commits](https://www.conventionalcommits.org/ja/v1.0.0/) を使用しています：

```
種類(スコープ): 命令形の要約、末尾にピリオドなし

任意の本文：変更の「なぜ」を書き、「どのように」は書かない。
1 行は約 72 文字で折り返す。

Fixes #123
```

- **種類**：`feat`、`fix`、`docs`、`i18n`、`perf`、`refactor`、`test`、`chore`。
- **スコープ**（任意）：`engine`、`parser`、`remote`、`voice`、`editor`、`android`、`linux`、`l10n`…

| ✅ 良い例 | ❌ 悪い例 |
|---|---|
| `fix(engine): stop exactly on pause markers at high WPM` | `arreglos` |
| `feat(remote): add follower role to the protocol` | `cambios varios en remote y engine y docs` |
| `docs(protocol): document cmd.goto payload` | `Update PROTOCOL.md` |

> **メモ：** マージ時にブランチのコミットは 1 つにまとめられる（*squash*）ため、最も重要なのは **PR のタイトル**です。これが最終的なコミットメッセージになります。

## Pull Request を作成する

### 1. ブランチを更新する

```bash
git fetch upstream
git rebase upstream/develop
git push origin fix/pause-marker-skip
```

### 2. `develop` に向けて PR を作成する

GitHub で「Compare & pull request」をクリックし、次を確認します：

- **base repository:** `GNUXDAR/PromptFlow`、**base:** `develop`
- **head repository:** あなたのフォーク、**compare:** あなたのブランチ

### 3. タイトル

コミットと同じ形式に従います：`種類(スコープ): 要約`。これが最終的なコミットのメッセージになります。

### 4. 説明

PR テンプレートは自動で入力されます。良い PR は次の 4 つの問いに答えています：

1. **何が変わるのか？** 1〜2 文での要約。
2. **なぜか？** 解決する問題と、issue へのリンク：`Fixes #123`（マージ時にクローズ）または `Refs #123`（言及のみ）。
3. **どうテストするか？** レビュアーが結果を再現できる具体的な手順。
4. **何を確認したか？** テンプレートのチェックリストに正直にチェックを入れること。テストできなかったことがあれば（たとえば Android 端末を持っていない）、そう書いてください。

見た目に関わる変更なら、**変更前と変更後**のスクリーンショットか短い動画を添えてください。

> **良い説明の例**
>
> 300 WPM を超える速度で 2 つのマーカーが同じ行にあると、エンジンが `[PAUSE 2s]` マーカーを読み飛ばしていました。1 フレームにつき 1 つのマーカーしか処理していなかったためです。
>
> Fixes #42
>
> **テスト方法：** `test/fixtures/double_pause.md` を 350 WPM で開くと、2 回停止するはずです。
>
> - [x] 新しいテスト `pausa doble en la misma línea`（修正なしでは失敗する）
> - [x] `flutter analyze` / `flutter test`
> - [ ] Android でテスト済み（端末を持っていない）

### 5. ドラフト PR

未完成の作業について早めに意見がほしい場合は、PR を **Draft** として作成してください。準備ができたら「Ready for review」にします。

### 6. 他の PR に依存する PR（スタック）

あなたの PR がまだマージされていない別の PR を必要とする場合は、その PR のブランチを base に設定し、説明に「#12 に依存」と書いてください。最初の PR がマージされると、GitHub が自動的に base を `develop` に切り替えます。

## レビューの流れ

### 期待できること

- **約 7 日以内**に最初の返信があります。2 週間以上音沙汰がなければ、PR にコメントしてリマインドしてください。歓迎します。
- 提案を含むコメントが 1 つ以上付きます。これは普通のことで、PR が悪いという意味ではありません。
- 自動チェック（解析とテスト）に合格する必要があります。

### コメントへの対応

- 同じブランチに**新しいコミット**として変更を加えてください。誰かがレビューした後に履歴を書き換えない（`push --force`）でください：そうすればレビュアーは変更点だけを確認できます。
- 各コメントに返信してください：「abc123 で対応しました」、あるいは別の案を提案する理由を説明します。根拠を持って異論を述べることも良いレビューの一部です。
- 会話を始めた人が、その会話を解決済みにします。

### 承認の基準

PR は次の条件を満たすとマージされます：

- [ ] 1 つのことだけを行い、説明で「何を」と「なぜ」が説明されている。
- [ ] このガイドのアーキテクチャと規約を守っている。
- [ ] 新しいロジックにテストがあり、すべてのチェックに合格している。
- [ ] UI テキストが `lib/l10n/` にある。
- [ ] 影響を受けるドキュメントが更新されている。
- [ ] 少なくとも 1 人のメンテナーが承認している。

マージはメンテナーが `develop` に対して **Squash and merge** で行います。

## マージの後

- ブランチを削除します（GitHub にボタンがあります）。
- フォークを同期します：
  ```bash
  git switch develop
  git fetch upstream
  git merge --ff-only upstream/develop
  git push origin develop
  ```
- あなたの変更は次のリリースで `main` に入ります。

## 翻訳

UI のテキストは `lib/l10n/app_<言語>.arb` にあります。基準となるファイルは `app_en.arb` です。

- **翻訳の修正：** その言語の `.arb` を編集し、`i18n/…` の PR を作成します。
- **言語の追加：** `app_en.arb` を `app_<コード>.arb` としてコピーし、**値だけ**を翻訳して（キーや `{placeholders}` は決して翻訳しない）、`flutter gen-l10n` で確認します。
- **翻訳されたドキュメント：** `docs/i18n/<言語>/` にあります。スペイン語の原文が優先されます：ドキュメントを変更した場合は、翻訳が古くなることを PR で知らせるか、翻訳も更新してください。

## エチケットと行動規範

このプロジェクトは [Contributor Covenant 2.1](https://www.contributor-covenant.org/ja/version/2/1/code_of_conduct/) に従います。要約すると：

- 親切で忍耐強く：すべての PR とレビューの向こうには、自由な時間を割いている人がいます。
- 批判するのはコードであって、人ではありません。
- 善意を前提とし、決めつける前に質問しましょう。
- スペイン語でも英語でも、好きな方で書いてください。

受け入れられない行為は、機密扱いの issue または GitHub のダイレクトメッセージで、メンテナーに非公開で報告できます。

## ヘルプを得る

- **やり方がわからない：** `question` ラベルを付けて issue を作成してください。
- **自分の PR についての疑問：** その PR で質問してください。
- **プロジェクトのリファレンス：** [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md) と [`docs/PROTOCOL.md`](../en/PROTOCOL.md)。
