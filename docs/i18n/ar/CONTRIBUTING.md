## طرق المساهمة

المساهمة ليست كودًا فقط. كل هذه المساهمات قيّمة:

| النوع | أمثلة |
|---|---|
| **الإبلاغ عن الأخطاء** | شيء لا يعمل، أو يظهر بشكل غير صحيح، أو التمرير غير سلس على جهازك. |
| **اقتراح الأفكار** | ميزة جديدة، أو اختصار، أو صيغة نص. |
| **الكود** | إصلاحات، وميزات، وأداء، واختبارات. |
| **التوثيق** | أخطاء إملائية، وتوضيحات، وأمثلة، ومخططات. |
| **الترجمات** | لغات جديدة أو تحسينات على اللغات الموجودة ([انظر أدناه](#الترجمات)). |
| **الاختبار على الأجهزة** | دواسات Bluetooth، والأجهزة اللوحية، وRaspberry Pi، وشبكات Wi‑Fi التي تفعّل عزل العملاء. |
| **مراجعة طلبات الدمج** | تجربة طلب دمج لشخص آخر والتعليق على ما لاحظته. |

## قبل أن تبدأ

### ابحث إن كان موجودًا بالفعل

قبل فتح issue أو البدء في البرمجة، ابحث في الـ [issues](https://github.com/GNUXDAR/PromptFlow/issues) وطلبات الدمج ([pull requests](https://github.com/GNUXDAR/PromptFlow/pulls)) المفتوحة. إن كان أحدهم يعمل بالفعل على الأمر نفسه، فعلّق هناك بدلًا من تكرار الجهد.

### افتح issue للتغييرات الكبيرة

| حجم التغيير | هل يلزم فتح issue أولًا؟ |
|---|---|
| خطأ إملائي، أو رابط معطّل، أو نص مُربك | لا: افتح طلب الدمج مباشرة. |
| إصلاح خطأ صغير وواضح | يُستحسن، وليس إلزاميًا. |
| ميزة جديدة، أو تغيير في السلوك، أو تغيير في البروتوكول أو البنية المعمارية | **نعم.** الاتفاق على النهج مسبقًا يجنّبك رفض عملك بسبب خلاف في التصميم. |

> **نصيحة:** علّق في الـ issue بعبارة «سأتولى هذا» حتى لا يأخذه أحد غيرك. وإن لم تتمكن من المتابعة لاحقًا، فأخبرنا: لا مشكلة في ذلك.

### issues للبدء

الـ issues التي تحمل الوسم `good first issue` محددة النطاق ومشروحة لمن يأتي لأول مرة. أما التي تحمل `help wanted` فهي مهمة وتبحث عن متطوعين.

## تجهيز بيئة العمل

### المتطلبات

- [Flutter](https://docs.flutter.dev/get-started/install) الإصدار المستقر (Dart 3).
- Linux: اعتماديات Flutter لسطح المكتب (`clang`، `cmake`، `ninja-build`، `libgtk-3-dev`).
- Android (اختياري): Android SDK وجهاز أو محاكي.

### الـ Fork والاستنساخ

```bash
# 1. أنشئ fork من GitHub (زر «Fork») ثم استنسخه
git clone https://github.com/<اسم-المستخدم>/PromptFlow.git
cd PromptFlow

# 2. أضف المستودع الأصلي باسم «upstream»
git remote add upstream https://github.com/GNUXDAR/PromptFlow.git

# 3. ثبّت الاعتماديات وتحقق من أن كل شيء يعمل
flutter pub get
flutter analyze
flutter test
```

### الصوت (اختياري)

```bash
tool/setup_vosk_linux.sh      # libvosk + النموذج الإسباني لنظام Linux
```

## نموذج الفروع

| الفرع | الغرض منه | من يكتب فيه؟ |
|---|---|---|
| `main` | الإصدارات المنشورة. مستقر دائمًا. | المشرفون فقط، عند نشر إصدار. |
| `develop` | دمج ما سيُنشر لاحقًا. **وجهة جميع طلبات الدمج.** | لا أحد مباشرة: فقط عبر طلب دمج. |
| `tipo/descripcion` | عملك. فرع واحد لكل موضوع. | أنت. |

> **مهم:** لا تُنشئ commits مباشرة على `main` أو `develop` أبدًا، ولا تفتح طلب دمج مقابل `main`. كل شيء يدخل عبر طلب دمج إلى `develop`.

### أسماء الفروع

استخدم `tipo/descripcion-corta` بأحرف صغيرة وبشرطات:

| البادئة | الاستخدام | مثال |
|---|---|---|
| `feat/` | ميزة جديدة | `feat/follower-mode` |
| `fix/` | إصلاح خطأ | `fix/pause-marker-skip` |
| `docs/` | توثيق فقط | `docs/protocol-examples` |
| `i18n/` | ترجمات | `i18n/add-turkish` |
| `perf/` | أداء | `perf/painter-culling` |
| `refactor/` | إعادة تنظيم دون تغيير في السلوك | `refactor/controller-commands` |
| `test/` | اختبارات فقط | `test/remote-reconnect` |
| `chore/` | البناء، والاعتماديات، وCI | `chore/bump-flutter` |

```bash
git fetch upstream
git switch -c fix/pause-marker-skip upstream/develop
```

## إجراء تغييراتك

### طلب دمج واحد، موضوع واحد

يجب أن يقوم طلب الدمج **بشيء واحد فقط**. إن كنت تصلح خطأً واكتشفت خطأً آخر، فافتح طلبَي دمج. تُراجَع طلبات الدمج الصغيرة أسرع وبعناية أكبر.

| الحجم | التوصية |
|---|---|
| < 200 سطر | مثالي. |
| 200–600 سطر | مقبول؛ اشرح البنية جيدًا في الوصف. |
| > 600 سطر | قسّمه إلى عدة طلبات دمج، أو افتح issue لتخطيط الأجزاء. |

### احترم البنية المعمارية

اقرأ [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md) قبل لمس الكود. أكثر القواعد التي تُراجَع هي:

- لا يعتمد `domain/` على عناصر واجهة Flutter (widgets) ولا على المقابس ولا على الملفات.
- كل إجراء تحكم هو `PrompterCommand` ويمر عبر `PrompterController.execute`، سواء جاء من لوحة المفاتيح أو الدواسة أو جهاز التحكم عن بُعد أو الصوت.
- لا شيء داخل حلقة الرسوم المتحركة يعيد بناء عناصر الواجهة في كل إطار.
- إن غيّرت البروتوكول، فحدّث [`docs/PROTOCOL.md`](../en/PROTOCOL.md). وإن كان التغيير يكسر التوافق، فارفع قيمة الحقل `v`.
- النصوص الظاهرة للمستخدم توضع في `lib/l10n/`، ولا تُكتب مباشرة في الكود أبدًا (انظر [الترجمات](#الترجمات)).

### الاختبارات

- يجب أن يرافق كل إصلاحِ خطأٍ اختبارٌ يفشل من دون الإصلاح.
- يجب أن ترافق كل ميزة جديدة تحتوي على منطق (المحرك، المحلل، البروتوكول، الصوت) اختبارات.
- لمحرك التمرير استخدم `ScrollEngine.manual()` و`advance()`: الاختبارات حتمية ولا تعتمد على الساعة.

### قبل الرفع

```bash
dart format lib test integration_test
flutter analyze        # دون تحذيرات
flutter test           # كل شيء ناجح
```

## رسائل commit

نستخدم [Conventional Commits](https://www.conventionalcommits.org/ar/v1.0.0/):

```
النوع(النطاق): ملخص بصيغة الأمر، دون نقطة في النهاية

متن اختياري: سبب التغيير، لا كيفيته.
اجعل طول الأسطر نحو 72 حرفًا.

Fixes #123
```

- **النوع**: `feat`، `fix`، `docs`، `i18n`، `perf`، `refactor`، `test`، `chore`.
- **النطاق** (اختياري): `engine`، `parser`، `remote`، `voice`، `editor`، `android`، `linux`، `l10n`…

| ✅ صحيح | ❌ خطأ |
|---|---|
| `fix(engine): stop exactly on pause markers at high WPM` | `arreglos` |
| `feat(remote): add follower role to the protocol` | `cambios varios en remote y engine y docs` |
| `docs(protocol): document cmd.goto payload` | `Update PROTOCOL.md` |

> **ملاحظة:** تُدمج commits فرعك في commit واحد (*squash*) عند الدمج، لذا فإن الأهم هو **عنوان طلب الدمج**، الذي يصبح الرسالة النهائية.

## فتح pull request

### 1. حدّث فرعك

```bash
git fetch upstream
git rebase upstream/develop
git push origin fix/pause-marker-skip
```

### 2. أنشئ طلب الدمج مقابل `develop`

على GitHub، اضغط «Compare & pull request» وتحقق من:

- **base repository:** `GNUXDAR/PromptFlow`، **base:** `develop`
- **head repository:** الـ fork الخاص بك، **compare:** فرعك

### 3. العنوان

اتبع الصيغة نفسها المستخدمة في الـ commits: `النوع(النطاق): ملخص`. سيكون هو رسالة الـ commit النهائي.

### 4. الوصف

يُملأ قالب طلب الدمج تلقائيًا. يجيب طلب الدمج الجيد عن أربعة أسئلة:

1. **ما الذي يتغير؟** ملخص في جملة أو جملتين.
2. **لماذا؟** المشكلة التي يحلها، مع رابط إلى الـ issue: `Fixes #123` (يغلقه عند الدمج) أو `Refs #123` (يشير إليه فقط).
3. **كيف أختبره؟** خطوات محددة تتيح للمراجع إعادة إنتاج النتيجة.
4. **ما الذي تحققت منه؟** قائمة التحقق في القالب، مؤشَّرًا عليها بأمانة. إن كان هناك ما لم تستطع اختباره (مثلًا، ليس لديك جهاز Android)، فاذكر ذلك.

إن كان التغيير مرئيًا، فأضف لقطات شاشة أو مقطع فيديو قصيرًا **قبل التغيير وبعده**.

> **مثال على وصف جيد**
>
> كان المحرك يتخطى العلامة `[PAUSE 2s]` عندما تقع علامتان في السطر نفسه بسرعة تزيد على 300 WPM، لأنه كان يعالج علامة واحدة فقط في كل إطار.
>
> Fixes #42
>
> **طريقة الاختبار:** افتح `test/fixtures/double_pause.md` بسرعة 350 WPM؛ يجب أن يتوقف مرتين.
>
> - [x] اختبار جديد `pausa doble en la misma línea` (يفشل من دون الإصلاح)
> - [x] `flutter analyze` / `flutter test`
> - [ ] جُرّب على Android (ليس لدي جهاز)

### 5. طلب دمج مسودة

إن أردت رأيًا مبكرًا في عمل لم يكتمل، فافتح طلب الدمج بوصفه **Draft**. ثم علّمه بـ «Ready for review» عندما يصبح جاهزًا.

### 6. طلبات دمج تعتمد على غيرها (مكدّسة)

إن كان طلب الدمج الخاص بك يحتاج إلى طلب آخر لم يُدمج بعد، فاجعل فرع ذلك الطلب هو الأساس (base) واذكر ذلك في الوصف: «يعتمد على #12». عند دمج الطلب الأول، سيغيّر GitHub الأساس إلى `develop` تلقائيًا.

## عملية المراجعة

### ما الذي تتوقعه

- ردّ أول في غضون **7 أيام تقريبًا**. إن مرّ أكثر من أسبوعين دون أخبار، فعلّق على طلب الدمج للتذكير: هذا مرحَّب به.
- تعليق واحد أو أكثر يتضمن اقتراحات. هذا أمر طبيعي ولا يعني أن طلب الدمج سيئ.
- يجب أن تنجح الفحوصات التلقائية (التحليل والاختبارات).

### الرد على التعليقات

- أجرِ التغييرات في **commits جديدة** على الفرع نفسه. لا تُعِد كتابة السجل (`push --force`) بعد أن يراجع أحدهم عملك: بهذا يرى المراجع ما تغيّر فقط.
- ردّ على كل تعليق: «تم في abc123» أو اشرح لماذا تقترح شيئًا آخر. الاختلاف المدعوم بالحجج جزء من المراجعة الجيدة.
- من فتح النقاش هو من يعلّمه بأنه محلول.

### معايير الموافقة

يُدمج طلب الدمج عندما:

- [ ] يقوم بشيء واحد فقط، ويشرح الوصف ماذا ولماذا.
- [ ] يحترم البنية المعمارية والأعراف الواردة في هذا الدليل.
- [ ] يتضمن اختبارات للمنطق الجديد وتنجح جميع الفحوصات.
- [ ] نصوص الواجهة موجودة في `lib/l10n/`.
- [ ] التوثيق المتأثر محدَّث.
- [ ] وافق عليه مشرف واحد على الأقل.

يتولى أحد المشرفين الدمج باستخدام **Squash and merge** على `develop`.

## بعد الدمج

- احذف فرعك (يوفر GitHub زرًا لذلك).
- زامن الـ fork الخاص بك:
  ```bash
  git switch develop
  git fetch upstream
  git merge --ff-only upstream/develop
  git push origin develop
  ```
- سيصل تغييرك إلى `main` في الإصدار المنشور التالي.

## الترجمات

نصوص الواجهة موجودة في `lib/l10n/app_<اللغة>.arb`. الملف المرجعي هو `app_en.arb`.

- **تصحيح ترجمة:** عدّل ملف `.arb` الخاص بتلك اللغة وافتح طلب دمج `i18n/…`.
- **إضافة لغة:** انسخ `app_en.arb` باسم `app_<الرمز>.arb`، وترجم **القيم فقط** (لا تترجم المفاتيح ولا `{placeholders}` أبدًا)، ثم تحقق باستخدام `flutter gen-l10n`.
- **التوثيق المترجم:** موجود في `docs/i18n/<اللغة>/`. الأصل الإسباني هو المرجع: إن غيّرت وثيقة، فنبّه في طلب الدمج إلى أن الترجمات أصبحت غير محدّثة، أو حدّثها.
