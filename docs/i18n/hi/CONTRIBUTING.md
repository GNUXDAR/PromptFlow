# PromptFlow में योगदान की गाइड

> यह [मूल स्पेनिश दस्तावेज़](../../../CONTRIBUTING.md) का अनुवाद है। यदि दोनों में अंतर हो, तो मूल दस्तावेज़ मान्य होगा।

PromptFlow में रुचि लेने के लिए धन्यवाद! यह गाइड बताती है कि बदलाव कैसे प्रस्तावित करें, किसी टाइपो को ठीक करने से लेकर पूरी नई सुविधा जोड़ने तक। इसे पहली बार ऊपर से नीचे तक पढ़ने और बाद में ज़रूरत के अनुसार अलग-अलग सेक्शन देखने के लिए लिखा गया है।

> **नोट:** अगर यह किसी ओपन सोर्स प्रोजेक्ट में आपका पहला योगदान है, तो सब कुछ परफ़ेक्ट करने की चिंता न करें। अच्छी नीयत से बनाया गया छोटा PR, कोई PR न होने से बेहतर है; बाकी में हम रिव्यू के दौरान आपकी मदद करेंगे।

## योगदान के तरीके

सब कुछ कोड ही नहीं है। ये सभी योगदान मूल्यवान हैं:

| प्रकार | उदाहरण |
|---|---|
| **बग रिपोर्ट करना** | कुछ काम नहीं कर रहा, ठीक से नहीं दिख रहा, या आपके डिवाइस पर स्क्रॉल स्मूद नहीं है। |
| **विचार सुझाना** | कोई नई सुविधा, कोई शॉर्टकट, कोई स्क्रिप्ट फ़ॉर्मैट। |
| **कोड** | सुधार, सुविधाएँ, परफ़ॉर्मेंस, टेस्ट। |
| **दस्तावेज़** | टाइपो, स्पष्टीकरण, उदाहरण, डायग्राम। |
| **अनुवाद** | नई भाषाएँ या मौजूदा भाषाओं में सुधार ([नीचे देखें](#अनुवाद))। |
| **हार्डवेयर पर टेस्ट** | ब्लूटूथ पैडल, टैबलेट, Raspberry Pi, क्लाइंट आइसोलेशन वाले Wi‑Fi नेटवर्क। |
| **PR रिव्यू करना** | किसी और का PR आज़माना और जो आपने देखा उस पर टिप्पणी करना। |

## शुरू करने से पहले

### देखें कि क्या यह पहले से मौजूद है

कोई issue खोलने या कोड लिखना शुरू करने से पहले, खुले हुए [issues](https://github.com/GNUXDAR/PromptFlow/issues) और [pull requests](https://github.com/GNUXDAR/PromptFlow/pulls) में खोजें। अगर कोई पहले से उसी पर काम कर रहा है, तो मेहनत दोहराने के बजाय वहीं टिप्पणी करें।

### बड़े बदलावों के लिए issue खोलें

| बदलाव का आकार | क्या पहले issue चाहिए? |
|---|---|
| टाइपो, टूटा हुआ लिंक, उलझा हुआ टेक्स्ट | नहीं: सीधे PR खोलें। |
| किसी छोटे और स्पष्ट बग का सुधार | सुझाया जाता है, अनिवार्य नहीं। |
| नई सुविधा, व्यवहार में बदलाव, प्रोटोकॉल या आर्किटेक्चर में बदलाव | **हाँ।** पहले से तरीके पर सहमति बना लेने से आपका काम डिज़ाइन पर असहमति के कारण अस्वीकार होने से बचता है। |

> **सुझाव:** issue में «यह मैं संभाल लूँगा/लूँगी» लिखें ताकि कोई और उसे न उठाए। अगर बाद में आप आगे न बढ़ पाएँ, तो बता दें: कोई बात नहीं।

### शुरुआत के लिए issues

`good first issue` लेबल वाले issues सीमित दायरे के हैं और पहली बार आने वालों के लिए समझाए गए हैं। `help wanted` वाले issues महत्वपूर्ण हैं और उनके लिए स्वयंसेवक चाहिए।

## परिवेश तैयार करना

### आवश्यकताएँ

- [Flutter](https://docs.flutter.dev/get-started/install) stable (Dart 3)।
- Linux: Flutter की डेस्कटॉप निर्भरताएँ (`clang`, `cmake`, `ninja-build`, `libgtk-3-dev`)।
- Android (वैकल्पिक): Android SDK और एक डिवाइस या एम्युलेटर।

### Fork और क्लोन

```bash
# 1. GitHub पर fork करें («Fork» बटन) और उसे क्लोन करें

cd PromptFlow

# 2. मूल रिपॉज़िटरी को «upstream» के रूप में जोड़ें

# 3. निर्भरताएँ इंस्टॉल करें और जाँचें कि सब कुछ काम कर रहा है

flutter test
```

## अपने बदलाव करना

### एक PR, एक विषय

एक PR को **केवल एक काम** करना चाहिए। अगर आप एक बग ठीक करते हुए दूसरा बग खोज लेते हैं, तो दो PR खोलें। छोटे PR जल्दी और ज़्यादा ध्यान से रिव्यू होते हैं।

| आकार | सिफ़ारिश |
|---|---|
| < 200 पंक्तियाँ | आदर्श। |
| 200–600 पंक्तियाँ | स्वीकार्य; विवरण में संरचना को अच्छी तरह समझाएँ। |
| > 600 पंक्तियाँ | इसे कई PR में बाँटें, या हिस्सों की योजना बनाने के लिए issue खोलें। |

### आर्किटेक्चर का पालन करें

कोड छूने से पहले [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md) पढ़ें। रिव्यू में सबसे ज़्यादा जाँचे जाने वाले नियम ये हैं:

- `domain/` Flutter विजेट, सॉकेट या फ़ाइलों पर निर्भर नहीं करता।
- हर कंट्रोल एक्शन एक `PrompterCommand` है और `PrompterController.execute` से होकर गुज़रता है, चाहे वह कीबोर्ड, पैडल, रिमोट कंट्रोल या वॉइस से आए।
- एनिमेशन लूप के अंदर कुछ भी हर फ़्रेम पर विजेट दोबारा नहीं बनाता।
- अगर आप प्रोटोकॉल बदलते हैं, तो [`docs/PROTOCOL.md`](../en/PROTOCOL.md) अपडेट करें। अगर बदलाव संगतता तोड़ता है, तो `v` फ़ील्ड बढ़ाएँ।
- उपयोगकर्ता को दिखने वाले टेक्स्ट `lib/l10n/` में रहते हैं, कभी सीधे कोड में नहीं लिखे जाते ([अनुवाद](#अनुवाद) देखें)।

### टेस्ट

- हर बग सुधार के साथ एक ऐसा टेस्ट होना चाहिए जो सुधार के बिना फ़ेल हो।
- लॉजिक वाली हर नई सुविधा (इंजन, पार्सर, प्रोटोकॉल, वॉइस) के साथ टेस्ट होने चाहिए।
- स्क्रॉल इंजन के लिए `ScrollEngine.manual()` और `advance()` का इस्तेमाल करें: टेस्ट नियतात्मक (deterministic) होते हैं और घड़ी पर निर्भर नहीं करते।

### पुश करने से पहले

```bash
dart format lib test integration_test
flutter analyze        # कोई चेतावनी नहीं
flutter test           # सब सफल
```

## कमिट संदेश

हम [Conventional Commits](https://www.conventionalcommits.org/hi/v1.0.0/) का उपयोग करते हैं:

```
प्रकार(दायरा): आज्ञार्थक रूप में सारांश, अंत में पूर्ण विराम नहीं

वैकल्पिक बॉडी: बदलाव का कारण, तरीका नहीं।
पंक्तियों को लगभग 72 अक्षरों पर लपेटें।

Fixes #123
```

- **प्रकार**: `feat`, `fix`, `docs`, `i18n`, `perf`, `refactor`, `test`, `chore`।
- **दायरा** (वैकल्पिक): `engine`, `parser`, `remote`, `voice`, `editor`, `android`, `linux`, `l10n`…

| ✅ सही | ❌ गलत |
|---|---|
| `fix(engine): stop exactly on pause markers at high WPM` | `arreglos` |
| `feat(remote): add follower role to the protocol` | `cambios varios en remote y engine y docs` |
| `docs(protocol): document cmd.goto payload` | `Update PROTOCOL.md` |

> **नोट:** मर्ज करते समय आपकी ब्रांच के commits को एक में मिला दिया जाता है (*squash*), इसलिए सबसे ज़रूरी चीज़ **PR का शीर्षक** है, जो अंतिम संदेश बन जाता है।

## Pull request खोलना

### 1. अपनी ब्रांच अपडेट करें

```bash
git fetch upstream
git rebase upstream/develop
git push origin fix/pause-marker-skip
```

### 2. `develop` के विरुद्ध PR बनाएँ

GitHub पर «Compare & pull request» दबाएँ और जाँचें:

- **base repository:** `GNUXDAR/PromptFlow`, **base:** `develop`
- **head repository:** आपका fork, **compare:** आपकी ब्रांच

### 3. शीर्षक

commits वाला ही फ़ॉर्मैट अपनाएँ: `प्रकार(दायरा): सारांश`। यही अंतिम commit का संदेश होगा।

### 4. विवरण

PR टेम्पलेट अपने आप भर जाता है। एक अच्छा PR चार सवालों का जवाब देता है:

1. **क्या बदलता है?** एक या दो वाक्यों में सारांश।
2. **क्यों?** वह समस्या जो यह हल करता है, issue के लिंक के साथ: `Fixes #123` (मर्ज होने पर उसे बंद कर देता है) या `Refs #123` (केवल उल्लेख करता है)।
3. **मैं इसे कैसे टेस्ट करूँ?** ठोस कदम, ताकि रिव्यू करने वाला नतीजा दोहरा सके।
4. **आपने क्या जाँचा?** टेम्पलेट की चेकलिस्ट, ईमानदारी से टिक की हुई। अगर कुछ टेस्ट नहीं कर पाए (उदाहरण के लिए, आपके पास Android डिवाइस नहीं है), तो बताएँ।

अगर बदलाव दृश्य (visual) है, तो **पहले और बाद** के स्क्रीनशॉट या एक छोटा वीडियो जोड़ें।

> **अच्छे विवरण का उदाहरण**
>
> जब 300 WPM से ज़्यादा गति पर दो मार्कर एक ही पंक्ति में आते थे, तो इंजन `[PAUSE 2s]` मार्कर को छोड़ देता था, क्योंकि हर फ़्रेम में केवल एक मार्कर प्रोसेस होता था।
>
> Fixes #42
>
> **कैसे टेस्ट करें:** `test/fixtures/double_pause.md` को 350 WPM पर खोलें; इसे दो बार रुकना चाहिए।
>
> - [x] नया टेस्ट `pausa doble en la misma línea` (सुधार के बिना फ़ेल होता है)
> - [x] `flutter analyze` / `flutter test`
> - [ ] Android पर टेस्ट किया (मेरे पास डिवाइस नहीं है)

### 5. ड्राफ़्ट PR

अगर आप अधूरे काम पर जल्दी राय चाहते हैं, तो PR को **Draft** के रूप में खोलें। तैयार होने पर उसे «Ready for review» के रूप में चिह्नित करें।

### 6. दूसरे PR पर निर्भर PR (स्टैक्ड)

अगर आपके PR को किसी ऐसे दूसरे PR की ज़रूरत है जो अभी मर्ज नहीं हुआ है, तो उस PR की ब्रांच को base बनाएँ और विवरण में लिखें: «#12 पर निर्भर»। पहला PR मर्ज होने पर GitHub अपने आप base को `develop` में बदल देगा।

## रिव्यू की प्रक्रिया

### क्या उम्मीद करें

- **लगभग 7 दिनों** में पहला जवाब। अगर दो हफ़्ते से ज़्यादा समय तक कोई खबर न आए, तो याद दिलाने के लिए PR पर टिप्पणी करें: इसका स्वागत है।
- सुझावों के साथ एक या कई टिप्पणियाँ। यह सामान्य है और इसका मतलब यह नहीं कि PR खराब है।
- स्वचालित जाँचें (विश्लेषण और टेस्ट) पास होनी चाहिए।

### टिप्पणियों का जवाब देना

- बदलाव उसी ब्रांच पर **नए commits** में करें। किसी के रिव्यू कर लेने के बाद इतिहास दोबारा न लिखें (`push --force`): इससे रिव्यू करने वाला केवल वही देखता है जो बदला है।
- हर टिप्पणी का जवाब दें: «abc123 में कर दिया» या समझाएँ कि आप कुछ और क्यों प्रस्तावित कर रहे हैं। तर्क के साथ असहमति जताना अच्छे रिव्यू का हिस्सा है।
- जिसने चर्चा शुरू की, वही उसे हल (resolved) के रूप में चिह्नित करता है।

### स्वीकृति के मानदंड

एक PR तब मर्ज होता है जब:

- [ ] वह केवल एक काम करता है और विवरण बताता है कि क्या और क्यों।
- [ ] वह इस गाइड के आर्किटेक्चर और परंपराओं का पालन करता है।
- [ ] नए लॉजिक के लिए टेस्ट हैं और सभी जाँचें पास होती हैं।
- [ ] इंटरफ़ेस के टेक्स्ट `lib/l10n/` में हैं।
- [ ] प्रभावित दस्तावेज़ अपडेट किए गए हैं।
- [ ] कम से कम एक मेंटेनर ने इसे स्वीकृत किया है।

मर्ज कोई मेंटेनर `develop` पर **Squash and merge** के साथ करता है।

## मर्ज के बाद

- अपनी ब्रांच हटाएँ (GitHub इसके लिए एक बटन देता है)।
- अपने fork को सिंक करें:
  ```bash
  git switch develop
  git fetch upstream
  git merge --ff-only upstream/develop
  git push origin develop
  ```
- आपका बदलाव अगले प्रकाशित संस्करण में `main` तक पहुँचेगा।

## अनुवाद

इंटरफ़ेस के टेक्स्ट `lib/l10n/app_<भाषा>.arb` में हैं। संदर्भ फ़ाइल `app_en.arb` है।

- **किसी अनुवाद को सुधारना:** उस भाषा की `.arb` फ़ाइल संपादित करें और एक `i18n/…` PR खोलें।
- **नई भाषा जोड़ना:** `app_en.arb` को `app_<कोड>.arb` के रूप में कॉपी करें, **केवल मानों (values)** का अनुवाद करें (कभी भी कुंजियों (keys) या `{placeholders}` का नहीं) और `flutter gen-l10n` से जाँचें।
- **अनूदित दस्तावेज़:** `docs/i18n/<भाषा>/` में हैं। स्पेनिश मूल दस्तावेज़ ही मान्य है: अगर आप कोई दस्तावेज़ बदलते हैं, तो PR में बताएँ कि अनुवाद पुराने हो गए हैं, या उन्हें भी अपडेट करें।
