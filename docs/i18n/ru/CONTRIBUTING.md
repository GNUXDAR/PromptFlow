# Руководство для контрибьюторов PromptFlow

> Перевод с испанского оригинала. В случае расхождений приоритет имеет [оригинал](../../../CONTRIBUTING.md).

Спасибо за интерес к PromptFlow! В этом руководстве объясняется, как предлагать изменения — от исправления опечатки до добавления целой функции. В первый раз его стоит прочитать от начала до конца, а затем обращаться к нужным разделам.

> **Примечание:** если это ваш первый вклад в проект с открытым исходным кодом, не переживайте, что всё должно быть идеально. Небольшой PR с добрыми намерениями лучше, чем никакого; с остальным мы поможем на ревью.

## Способы внести вклад

Не всё сводится к коду. Ценен любой из этих видов участия:

| Вид | Примеры |
|---|---|
| **Сообщения об ошибках** | Что-то падает, отображается неправильно или прокрутка на вашем устройстве идёт рывками. |
| **Предложения идей** | Новая функция, горячая клавиша, формат сценария. |
| **Код** | Исправления, функции, производительность, тесты. |
| **Документация** | Опечатки, уточнения, примеры, диаграммы. |
| **Переводы** | Новые языки или улучшение существующих ([см. ниже](#переводы)). |
| **Тестирование на оборудовании** | Bluetooth-педали, планшеты, Raspberry Pi, сети Wi‑Fi с изоляцией клиентов. |
| **Ревью PR** | Проверить чужой PR и написать, что вы заметили. |

## Прежде чем начать

### Проверьте, нет ли этого уже

Прежде чем открывать issue или садиться за код, поищите среди открытых [issues](https://github.com/GNUXDAR/PromptFlow/issues) и [pull requests](https://github.com/GNUXDAR/PromptFlow/pulls). Если кто-то уже работает над тем же, напишите там, а не дублируйте усилия.

### Для крупных изменений сначала откройте issue

| Масштаб изменения | Нужен ли сначала issue? |
|---|---|
| Опечатка, битая ссылка, непонятный текст | Нет: сразу открывайте PR. |
| Исправление небольшого и понятного бага | Рекомендуется, но не обязательно. |
| Новая функция, изменение поведения, изменение протокола или архитектуры | **Да.** Согласовав подход заранее, вы избежите того, что работу отклонят из-за разногласий в дизайне. |

> **Совет:** напишите в issue «Беру на себя», чтобы никто другой за него не взялся. Если потом не сможете продолжить — просто сообщите об этом, ничего страшного.

### Issues для новичков

Issues с меткой `good first issue` чётко ограничены и описаны для тех, кто пришёл впервые. Issues с меткой `help wanted` важны и ждут добровольцев.

## Подготовка окружения

### Требования

- [Flutter](https://docs.flutter.dev/get-started/install) stable (Dart 3).
- Linux: зависимости Flutter для десктопа (`clang`, `cmake`, `ninja-build`, `libgtk-3-dev`).
- Android (необязательно): Android SDK и устройство или эмулятор.

### Форк и клонирование

```bash
# 1. Сделайте форк на GitHub (кнопка «Fork») и клонируйте его
git clone https://github.com/<ваш-пользователь>/PromptFlow.git
cd PromptFlow

# 2. Добавьте исходный репозиторий как «upstream»
git remote add upstream https://github.com/GNUXDAR/PromptFlow.git

# 3. Установите зависимости и убедитесь, что всё работает
flutter pub get
flutter analyze
flutter test
```

### Голос (необязательно)

```bash
tool/setup_vosk_linux.sh      # libvosk + испанская модель для Linux
```

## Модель веток

| Ветка | Назначение | Кто пишет? |
|---|---|---|
| `main` | Опубликованные версии. Всегда стабильна. | Только мейнтейнеры, при выпуске версии. |
| `develop` | Интеграция того, что войдёт в следующий выпуск. **Цель всех PR.** | Никто напрямую: только через PR. |
| `тип/описание` | Ваша работа. Одна ветка на одну тему. | Вы. |

> **Важно:** никогда не коммитьте напрямую в `main` или `develop` и не открывайте PR в `main`. Всё попадает через PR в `develop`.

### Имена веток

Используйте `тип/краткое-описание` в нижнем регистре, через дефисы:

| Префикс | Назначение | Пример |
|---|---|---|
| `feat/` | Новая функция | `feat/follower-mode` |
| `fix/` | Исправление бага | `fix/pause-marker-skip` |
| `docs/` | Только документация | `docs/protocol-examples` |
| `i18n/` | Переводы | `i18n/add-turkish` |
| `perf/` | Производительность | `perf/painter-culling` |
| `refactor/` | Реорганизация без изменения поведения | `refactor/controller-commands` |
| `test/` | Только тесты | `test/remote-reconnect` |
| `chore/` | Сборка, зависимости, CI | `chore/bump-flutter` |

```bash
git fetch upstream
git switch -c fix/pause-marker-skip upstream/develop
```

## Внесение изменений

### Один PR — одна тема

PR должен делать **что-то одно**. Если, исправляя баг, вы нашли ещё один, откройте два PR. Небольшие PR проверяют быстрее и внимательнее.

| Размер | Рекомендация |
|---|---|
| < 200 строк | Идеально. |
| 200–600 строк | Допустимо; хорошо опишите структуру в описании. |
| > 600 строк | Разбейте на несколько PR или откройте issue, чтобы спланировать части. |

### Соблюдайте архитектуру

Прочитайте [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md), прежде чем трогать код. Чаще всего на ревью проверяют следующие правила:

- `domain/` не зависит от виджетов Flutter, сокетов и файлов.
- Любое управляющее действие — это `PrompterCommand`, и оно проходит через `PrompterController.execute`, откуда бы ни пришло: с клавиатуры, педали, пульта или голосом.
- Ничто внутри цикла анимации не перестраивает виджеты на каждом кадре.
- Если вы меняете протокол, обновите [`docs/PROTOCOL.md`](../en/PROTOCOL.md). Если изменение нарушает совместимость, увеличьте поле `v`.
- Видимые пользователю тексты хранятся в `lib/l10n/` и никогда не пишутся прямо в коде (см. [Переводы](#переводы)).

### Тесты

- Каждое исправление бага должно сопровождаться тестом, который падает без этого исправления.
- Каждая новая функция с логикой (движок, парсер, протокол, голос) должна сопровождаться тестами.
- Для движка прокрутки используйте `ScrollEngine.manual()` и `advance()`: тесты детерминированы и не зависят от часов.

### Перед отправкой

```bash
dart format lib test integration_test
flutter analyze        # без предупреждений
flutter test           # всё зелёное
```

## Сообщения коммитов

Мы используем [Conventional Commits](https://www.conventionalcommits.org/ru/v1.0.0/):

```
тип(область): краткое описание в повелительном наклонении, без точки в конце

Необязательное тело: почему сделано изменение, а не как.
Переносите строки на ~72 символах.

Fixes #123
```

- **тип**: `feat`, `fix`, `docs`, `i18n`, `perf`, `refactor`, `test`, `chore`.
- **область** (необязательно): `engine`, `parser`, `remote`, `voice`, `editor`, `android`, `linux`, `l10n`…

| ✅ Хорошо | ❌ Плохо |
|---|---|
| `fix(engine): stop exactly on pause markers at high WPM` | `arreglos` |
| `feat(remote): add follower role to the protocol` | `cambios varios en remote y engine y docs` |
| `docs(protocol): document cmd.goto payload` | `Update PROTOCOL.md` |

> **Примечание:** при слиянии коммиты вашей ветки объединяются в один (*squash*), поэтому важнее всего **заголовок PR** — он становится итоговым сообщением коммита.

## Открытие pull request

### 1. Обновите свою ветку

```bash
git fetch upstream
git rebase upstream/develop
git push origin fix/pause-marker-skip
```

### 2. Создайте PR в `develop`

На GitHub нажмите «Compare & pull request» и проверьте:

- **base repository:** `GNUXDAR/PromptFlow`, **base:** `develop`
- **head repository:** ваш форк, **compare:** ваша ветка

### 3. Заголовок

Используйте тот же формат, что и для коммитов: `тип(область): краткое описание`. Это станет сообщением итогового коммита.

### 4. Описание

Шаблон PR подставляется автоматически. Хороший PR отвечает на четыре вопроса:

1. **Что меняется?** Краткое описание в одном-двух предложениях.
2. **Зачем?** Какую проблему это решает, со ссылкой на issue: `Fixes #123` (закрывает его при слиянии) или `Refs #123` (только упоминает).
3. **Как это проверить?** Конкретные шаги, чтобы ревьюер смог воспроизвести результат.
4. **Что вы проверили?** Чек-лист из шаблона, отмеченный честно. Если что-то проверить не удалось (например, у вас нет Android-устройства), так и напишите.

Если изменение визуальное, приложите скриншоты или короткое видео **до и после**.

> **Пример хорошего описания**
>
> Движок пропускал метку `[PAUSE 2s]`, когда две метки оказывались на одной строке при скорости выше 300 WPM, потому что за кадр обрабатывалась только одна метка.
>
> Fixes #42
>
> **Как проверить:** откройте `test/fixtures/double_pause.md` на 350 WPM; прокрутка должна остановиться дважды.
>
> - [x] Новый тест `pausa doble en la misma línea` (падает без исправления)
> - [x] `flutter analyze` / `flutter test`
> - [ ] Проверено на Android (нет устройства)

### 5. Черновик PR

Если хотите получить отзыв пораньше о незавершённой работе, откройте PR как **Draft**. Когда всё будет готово, отметьте его как «Ready for review».

### 6. PR, зависящие от других (стек)

Если вашему PR нужен другой, который ещё не влит, укажите в качестве базы ветку того PR и напишите об этом в описании: «Зависит от #12». Когда первый PR будет влит, GitHub автоматически сменит базу на `develop`.

## Процесс ревью

### Чего ожидать

- Первый ответ — **примерно в течение 7 дней**. Если прошло больше двух недель без новостей, напомните о себе комментарием в PR: это приветствуется.
- Один или несколько комментариев с предложениями. Это нормально и не означает, что PR плохой.
- Автоматические проверки (анализ и тесты) должны проходить.

### Ответы на комментарии

- Вносите изменения **новыми коммитами** в ту же ветку. Не переписывайте историю (`push --force`) после того, как кто-то провёл ревью: так ревьюер увидит только то, что изменилось.
- Отвечайте на каждый комментарий: «Сделано в abc123» — или объясните, почему предлагаете иначе. Аргументированное несогласие — часть хорошего ревью.
- Помечает обсуждение решённым тот, кто его начал.

### Критерии одобрения

PR вливается, когда:

- [ ] Он делает что-то одно, а описание объясняет, что и зачем.
- [ ] Он соблюдает архитектуру и соглашения из этого руководства.
- [ ] Для новой логики есть тесты, и все проверки проходят.
- [ ] Тексты интерфейса находятся в `lib/l10n/`.
- [ ] Затронутая документация обновлена.
- [ ] Его одобрил хотя бы один мейнтейнер.

Слияние выполняет мейнтейнер через **Squash and merge** в `develop`.

## После слияния

- Удалите свою ветку (GitHub предлагает для этого кнопку).
- Синхронизируйте свой форк:
  ```bash
  git switch develop
  git fetch upstream
  git merge --ff-only upstream/develop
  git push origin develop
  ```
- Ваше изменение попадёт в `main` со следующим опубликованным выпуском.

## Переводы

Тексты интерфейса находятся в `lib/l10n/app_<язык>.arb`. Эталонный файл — `app_en.arb`.

- **Исправить перевод:** отредактируйте `.arb` нужного языка и откройте PR `i18n/…`.
- **Добавить язык:** скопируйте `app_en.arb` как `app_<код>.arb`, переведите **только значения** (никогда не ключи и не `{placeholders}`) и проверьте командой `flutter gen-l10n`.
- **Переведённая документация:** находится в `docs/i18n/<язык>/`. Приоритет имеет испанский оригинал: если вы меняете документ, укажите в PR, что переводы устарели, или обновите их.

## Этикет и кодекс поведения

Проект следует [Contributor Covenant 2.1](https://www.contributor-covenant.org/ru/version/2/1/code_of_conduct/). Вкратце:

- Будьте доброжелательны и терпеливы: за каждым PR и каждым ревью стоит человек, который тратит на это своё свободное время.
- Критикуйте код, а не людей.
- Исходите из добрых намерений и спрашивайте, прежде чем делать выводы.
- Пишите на испанском или английском — как вам удобнее.

О недопустимом поведении можно сообщить мейнтейнерам в частном порядке — через issue с пометкой «конфиденциально» или личным сообщением на GitHub.

## Где получить помощь

- **Вопросы о том, как что-то сделать:** откройте issue с меткой `question`.
- **Вопросы по вашему PR:** спрашивайте в самом PR.
- **Справочные документы проекта:** [`docs/ARCHITECTURE.md`](../en/ARCHITECTURE.md) и [`docs/PROTOCOL.md`](../en/PROTOCOL.md).

Спасибо за ваш вклад! 💛
